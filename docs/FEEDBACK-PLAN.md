### 인라인 수정(기회-7) 구현 방침
- 필드 클릭 → 입력 전환 → **blur 또는 Enter 로 저장**, Esc 로 취소
- 낙관적 업데이트 + 실패 시 롤백 + toast (칸반 전이와 같은 방식)
- 저장은 기존 `PATCH /api/opportunities/:id` 재사용
- **단계 변경은 `PATCH .../stage` 를 쓴다** — `opportunity-stage.ts` 경유 원칙 유지(AGENTS.md)
- 접근성: 키보드로 진입·저장·취소 가능해야 함(ACC_*)

### 브레드크럼

## D. 거래처 담당자 다중화 (1건) — 스키마 변경

| # | 원문 |
|---|---|
| 거래처-8 | 거래처에서 담당자 **여러 명** 작성 필요, **대표 담당자만** 리스트 페이지에서 표출 |

현재 `Account` 는 담당자를 단일 필드로 갖는다(`contactName` · `position` · `phone` · `email`).

### 제안 스키마
```prisma
model Contact {
  id        String  @id @default(cuid())
  orgId     String
  accountId String
  account   Account @relation(fields: [accountId], references: [id], onDelete: Cascade)
  name      String
  position  String?
  phone     String?
  email     String?
  isPrimary Boolean @default(false)   // 대표 담당자
  ...
}
```
- `Account` 의 기존 4개 단일 필드는 **마이그레이션에서 Contact 1건으로 옮기고 제거**한다.
- 대표 담당자는 거래처당 1명 — 앱 레벨에서 보장(SQLite 부분 유니크 제약이 까다로움).
- 목록에는 대표 담당자만, 상세에서 전체 관리(추가·수정·삭제·대표 지정).

⚠️ **기존 데이터 이관이 필요한 유일한 항목**이다. 시드도 함께 갱신한다.

### 기회-6 예상 금액 — **확정 문서 기준** (결정됨)

합계나 "최신 견적서" 같은 암묵적 규칙 대신 **확정 문서 1건**을 두고 그 금액을 쓴다.
금액이 어느 문서에서 왔는지 화면에 드러나고, 견적서 1차·2차가 쌓여도 예측 가능하다.

**스키마**: `Opportunity.confirmedDocumentId` (nullable FK, named relation)
`Document.isConfirmed` 플래그보다 낫다 — 기회당 확정 문서가 **구조적으로 1건**으로 보장되고
"여러 문서가 동시에 확정" 상태가 만들어질 수 없다. `Opportunity` 에 자기참조 관계(다음 기회 체인)가
이미 있어 named relation 선례가 있다.

**① 자동 판정 (기본 동작)**

| 우선순위 | 문서 상태 |
|---|---|
| 1 | 계약완료 (COMPLETED) |
| 2 | 발송완료 (SENT) |
| 3 | 초안 (DRAFT) |
| — | **폐기(VOID)는 대상에서 제외** |

동순위는 최근 수정 순. 재판정 시점은 **문서 연결 · 상태 변경 · 금액 변경** 세 가지다.
판정은 순수 함수로 분리해 tsx 로 검증한다.

**② 변경 알림**

자동 판정으로 확정 문서가 바뀌면 금액이 소리 없이 달라진다. 반드시 알린다.

```
예상 금액이 ₩52,000,000 으로 바뀌었습니다 — 2차 견적서 기준   [되돌리기]
```

모달이 아니라 **toast** 로 한다. 작업 흐름을 막지 않으면서 되돌릴 길을 준다.

**③ 수동 고정**

사용자가 연관 문서 목록에서 다른 문서를 확정으로 지정하면 **그 기회는 자동 판정에서 제외(잠금)** 된다.
상세 화면에 "자동 판정으로 되돌리기" 를 둔다. 별도 설정 화면 없이 잠금 상태 자체가 자동/수동 스위치가 된다.

**④ 확정 문서가 없을 때 → ₩0**

수동 입력을 허용하지 않는다. 화면에는 `₩0 · 확정 문서 없음` 으로 표시하고 문서를 연결하도록 유도한다.

> ⚠️ **시드 재구성 필요**: 현재 시드는 기회 12건 중 문서가 연결된 것이 2건뿐이다.
> ₩0 규칙을 적용하면 파이프라인 합계가 **₩657,000,000 → 약 ₩96,000,000** 으로 급락한다.
> Phase 7 대시보드가 의미 있는 그림을 그리려면 **대부분의 기회에 문서를 연결하도록 시드를 다시 짠다.**
> 단계별 분포(초기·제안·검토/협상·수주·실주)와 문서 상태(초안·발송완료·계약완료)를 함께 배분한다.

### ⚠️ 남은 미결 사항

**기회-5 문장이 잘려 있음**
> "문서 생성 시 두가지 스텝으로 설정 (1. 새 문서 생성, 2. 기존 문서 선택 (기존 문서 선택 시 "

괄호가 열린 채 끝나 뒤 내용을 알 수 없다.
**가정**: "기존 문서 선택" 은 보관함의 문서를 **이 기회에 연결**하는 것으로 본다(복제 아님).
확정 문서 개념과도 맞물린다 — 연결되면 자동 판정 대상에 들어간다.
다르게 의도하셨다면 E 그룹 착수 전에 알려주시면 된다.

## 진행 순서

```
A (결함 수정)  ─┐
B (목록 공통)  ─┼─▶ 서로 독립. 병렬 가능
D (담당자 다중) ┘      단 D 는 스키마 → 마이그레이션 충돌 주의

C (상세 재구성) ──▶ A 완료 후 (스테퍼를 함께 손대므로)

E (문서·금액)  ──▶ D 와 마이그레이션이 겹치므로 D 다음
```

**D · E 는 둘 다 스키마를 건드린다.** 마이그레이션 충돌을 피하려면 **D → E 순서로 직렬 진행**하고,
같은 시점에 두 워커를 띄우지 않는다.

**권장**: A+B 를 한 워커로 먼저 처리해 눈에 보이는 결함을 걷어낸 뒤,
C 를 단독 워커로(가장 큼), D 를 별도 워커로(스키마 격리), E 는 결정 후 마지막.

## 원칙 (기존 유지)

- 단계 전이는 `@/lib/opportunity-stage` 경유. `stage` 직접 update 금지.
- 집계는 `@/lib/pipeline` 순수 함수.
- 모든 조회·수정·삭제에 `orgId` 스코프.
- 서버 컴포넌트 기본, 상호작용만 `_components/` 에 co-locate.
- UI 텍스트 한국어 존댓말(COPY-TONE), 접근성(ACC_*).
- 워크트리에서는 `next dev`·`next build` 불가 → `tsc`·`eslint`·`tsx` 로만 검증, 화면 확인은 메인 체크아웃.
