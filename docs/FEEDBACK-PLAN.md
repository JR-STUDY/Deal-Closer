### 1번 — 진행 단계를 이력에서 도출 (핵심)

원인은 `opportunityProgress(stage)` 가 **`stage` 하나만** 받았다는 것이다. 마감된 기회는
`stage` 가 `WON`·`LOST` 뿐이라 어디까지 갔었는지 알 수 없어, 트랙 3단계를 전부 "지나온"으로
칠하고 있었다. 상단은 stage 기반, 하단은 ActivityLog 기반 → **출처가 달라 어긋났다.**

- 시그니처: `opportunityProgress(stage, history?)` · `history` 는 `{ from, to }` 배열
  (활동 이력 `detail` 에서 꺼낸 값. 단계와 무관한 값·정의 밖 문자열·null 은 무시된다).
- 도달 지점 판정은 `reachedOpenStage(stage, history)` 로 분리했다 — `from`·`to` 를 **함께** 보므로
  중간 전이 기록이 유실돼도 마감 이력 한 줄(`from: PROPOSAL`)로 도달 지점이 잡힌다.
  이력 정렬 순서는 무관하다(최댓값으로 뽑는다 — 상세 화면은 시간 역순으로 읽는다).
- **진행 중인 기회는 이력을 보지 않는다** — 현재 단계가 곧 도달 지점이다. 그래서 마감을 풀어
  되돌린 기회(검토/협상 → 제안)는 검토/협상이 다시 **남은 단계**로 보인다(기준점은 하나뿐).
- **폴백**: 마감됐는데 이력이 없으면 **초기까지만** 지나온 것으로 본다. 모든 기회는 초기에서
  시작하므로(스키마 기본값) 이력 없이 확실히 말할 수 있는 최소 사실이다. 알 수 없는 구간을
  "지나온"으로 채우는 과대 주장이 바로 이 결함이었으니, 모르면 덜 주장하는 쪽으로 넘어진다.
- **쿼리는 늘지 않는다** — 상세 페이지가 이미 조회하는 ActivityLog 를 한 번만 파싱해
  이력 표시와 진행 단계 계산이 함께 쓴다. 칸반·목록은 이 함수를 쓰지 않는다(`StageBadge` 만 쓴다).

### 3번 — 방식 선택 근거

ⓘ 툴팁만으로는 부족하다. 이 줄은 안내 문구가 없어도 **금액 자릿수·건수에 따라 폭이 바뀌고**,
검색란이 `flex-1` 이라 남는 폭을 흡수하면서 그 변화를 그대로 되받았다. 그래서 근본 원인인
`flex-1` 을 걷어내 검색란을 고정 폭(`sm:w-72`)으로 바꾸고, 남는 폭은 가운데 빈 공간이 흡수하게 했다.
그 위에 안내 문구를 ⓘ(`src/components/info-hint.tsx`)로 접어 줄 길이 변동 자체를 줄였다.
툴팁 트리거는 버튼이라 **Tab 으로 초점을 받고 그때 열린다**(hover 전용 아님, ACC_*).
거래처 목록의 `(검색어: …)` 도 같은 문제(입력 글자 수만큼 늘어남)라 같은 방식으로 맞췄다.

### 5번 — 데이터 테이블 컬럼 폭도 흔들린다 (✅ 완료, `83c1760` · `59c9951` · `0813c75`)

**3번과 같은 부류다.** HTML 테이블은 기본적으로 내용에 맞춰 컬럼 폭을 자동 계산하므로,
행 내용이 바뀌면 표 전체가 다시 배치된다.

| 언제 흔들리나 | 예 |
|---|---|
| 페이지 이동 | 1쪽에 `₩180,000,000` 이 있고 2쪽엔 없으면 예상 금액 컬럼 폭이 달라진다 |
| 필터·검색 | 남은 행의 내용에 맞춰 다시 계산된다 |
| 거래처명 길이 | `Bluewave Systems Korea` 와 `세종테크` 가 섞이면 폭이 요동친다 |

**조치**: `table-layout: fixed` + **컬럼별 명시 폭**을 준다. 넘치는 텍스트는 말줄임으로 자르고
`title` 속성으로 전체를 볼 수 있게 한다(마우스 없이도 닿게 처리 — ACC_*).
**기회 목록과 거래처 목록 양쪽**에 같은 규칙을 적용한다. 3번에서 툴바를 고정 폭으로 맞췄으니
표까지 고정해야 화면 전체가 흔들리지 않는다.

숫자 컬럼(예상 금액)은 `tabular-nums` 로 자릿수 정렬을 맞춘다 —
폭을 고정해도 숫자 폭이 들쭉날쭉하면 여전히 어수선하다.

**반영 결과**: 두 목록에 `table-fixed` + 컬럼별 명시 폭(`min-w-[960px]`)을 넣었다. 남는 폭은
**기회명·회사명 한 칸만** 흡수하게 그 칸의 폭을 비워 뒀다 — 모든 칸에 폭을 적으면 잔여 폭이
비례 분배돼 배지 칸까지 같이 넓어진다. 말줄임은 `RowLink` 자신이 아니라 안쪽 `span`
(`::after` 덮개의 형제)에 맡겨 행 전체 클릭을 깨지 않았다.

**추가로 드러난 원인 — 본문 스크롤바.** 표를 고정한 뒤에도 기회명 칸이 655 ↔ 670 으로
15px 남아 있었다. 표가 아니라 본문 컨테이너(`overflow-auto p-8`) 때문이었다. 10행이면
세로 스크롤이 생겨 15px 을 먹고, 2행이면 사라지며 그 폭이 잔여 흡수 칸으로 몰린다.
`scrollbar-gutter: stable` 로 거터를 항상 예약해 없앴다.

같은 컨테이너가 **22개 화면에 같은 문자열로 반복**되므로 전 화면에 확대 적용했다
(표가 없는 화면도 같은 이유로 흔들린다). 다만 이 클래스 문자열 중복 자체는 남아 있다 —
공용 레이아웃 컴포넌트로 뽑는 것은 별도 정리 과제다.

| 측정 | 기회 1쪽(10행) | 기회 2쪽(2행) | `stage=WON` 필터 |
|---|---|---|---|
| 컬럼 폭 | 655/208/104/144/112/112/56 | 동일 | 동일 |
| 표 전체 | 1391px | 1391px | 1391px |

**부분 수정 병합(기회-7)** — 인라인은 고친 필드 하나만 보낸다. 검증 규칙을 두 벌로 나누는 대신
`withOpportunityDefaults()` 가 빠진 필드를 현재 값으로 채워 기존 `parseOpportunityInput()` 을
그대로 통과시킨다. **빈 문자열은 "비움"** 이므로 키 존재 여부로만 판단한다 — 값의 참·거짓으로
판단하면 마감일·메모를 지울 수 없다. 이 경계를 `scripts/opportunity-patch.test.ts` 가 지킨다.

**스테퍼 전이(기회-1)** — 스테퍼는 규칙을 스스로 판단하지 않는다. 허용 판정·경고 문구는
`@/lib/opportunity-transition`, 저장은 `POST /api/opportunities/:id/stage` → `opportunity-stage`
트랜잭션이며, 칸반과 같은 `useStageChange` 훅을 공유한다. `@/lib/opportunity-progress` 는
**읽기 전용 표시 모듈**로 남겨 전이 로직을 넣지 않았고, 진행 단계는 계속 이력 기반
(`opportunityProgress(stage, history)`)으로 도출한다 — 상단과 하단이 어긋나지 않아야 한다.
낙관 반영 중에는 방금 고른 전이를 이력에 얹어 계산해 지나온 구간이 흔들리지 않게 했다.

**마감 노드를 갈래로 벌리지 않았다** — 진행 중에는 수주·실주 중 어느 쪽인지 정해지지 않았으므로
노드 하나를 두고, 누르면 드롭다운으로 결과를 고른다(기회-11 결정 유지).

**문서 연결(기회-2)** — "양식화" 시나리오는 **이미 있는 공용 기준 양식을 열어줄 뿐**이라 연결하지
않는다(팀 공용 문서가 특정 기회에 묶이면 안 된다). 새로 만드는 두 경로만 `Document.opportunityId`
연결 + `DOCUMENT_CREATED` 이력을 **한 트랜잭션**으로 남긴다. 기회 id 는 서버가 orgId 로 다시
확인하고, 찾지 못하면 조용히 넘기지 않고 404 로 끊는다.

**이력 문서 요약(기회-13)** — 금액은 `ActivityLog.detail` 에 없으므로 문서에서 가져온다. 이력 줄마다
조회하면 N+1 이 되므로, 이 기회에 붙은 문서 목록(이미 조회함)으로 먼저 채우고 **연결이 끊긴
문서만 모아 한 번** 더 읽는다(없으면 조회 자체를 건너뛴다). 끝내 못 찾으면 금액은 비운다 —
0원과 "모름"은 다르다.

현재 `Account` 는 담당자를 단일 필드로 갖는다(`contactName` · `position` · `phone` · `email`).

### 제안 스키마
```prisma
model Contact {
  id        String  @id @default(cuid())
  orgId     String
  accountId String
  account   Account @relation(fields: [accountId], references: [id], onDelete: Cascade)
  name      String
  position  String?
  phone     String?
  email     String?
  isPrimary Boolean @default(false)   // 대표 담당자

```

⚠️ **기존 데이터 이관이 필요한 유일한 항목**이다. 시드도 함께 갱신한다.

### D 반영 결과

| 조치 | 대상 |
|---|---|
| `Contact` 모델 신설 · `Account` 의 담당자 4개 필드 제거 | `prisma/schema.prisma` |
| **데이터 이관 SQL 을 손으로 작성** (아래 참고) | `prisma/migrations/20260811045323_split_account_contacts/` |

**마이그레이션 — 순서가 곧 데이터 보존이다.** `prisma migrate dev` 가 자동 생성하는 SQL 은
컬럼을 그냥 버려 기존 담당자 정보가 통째로 사라진다. ① `contacts` 생성 → ② `accounts` 의 현재
값을 복사(`isPrimary = true`) → ③ `accounts` 재정의(4개 컬럼 제거) 순으로 손질했다.
Contact `id` 는 SQL 안에서 `cuid()` 를 쓸 수 없어 `'ct_' || accounts.id` 로 파생한다 —
거래처당 1건이라 유일성이 `Account.id` 로 보장되고, 어느 DB 에 돌려도 같은 값이 나온다.
`createdAt`·`updatedAt` 은 거래처 값을 물려받아 "가장 먼저 만들어진 담당자" 승격 규칙이
이관된 담당자에게도 자연스럽게 걸린다. **담당자명이 비어 있던 거래처는 Contact 를 만들지 않는다**
(`name` 이 필수이고, 이름 없는 담당자는 어디에도 표시할 수 없다).

**실데이터 검증** — 마이그레이션 직전 스냅샷 **복사본**에 적용해 확인했다(원본·개발 DB 미접근).
거래처 5곳의 담당자 5명이 값 손실 없이 이관됐고, 경계 확인용으로 넣은 담당자명 NULL·공백
거래처 2곳은 담당자 0명으로 남았다. FK 위반 0건, 대표 2명 이상인 거래처 0건,
기회 12·문서 42·이력 33건은 그대로였다.

### 판단이 필요했던 부분과 근거

| 논점 | 결정 | 근거 |
|---|---|---|
| 대표 유일성 | **앱 레벨**(트랜잭션) | `@@unique([accountId, isPrimary])` 는 "비대표도 1명뿐"이 되고, SQLite 부분 유니크 인덱스는 Prisma 스키마로 표현되지 않는다 |
| 대표 **해제** | 스스로 못 내려온다 | 내려올 수 있게 두면 담당자는 있는데 대표는 0명 → 목록에서 그 거래처의 담당자가 사라진다. 바꾸려면 다른 사람을 올린다 |
| 등록 폼의 담당자 | **받지 않는다** | 여러 명이 붙고 대표를 지정해야 해서 폼에 넣으면 "첫 한 명"만 특별해진다. 0명을 허용하므로 거래처 → 상세 순서로 안내 |
| 검색 범위 | 대표가 **아니어도** 걸린다 | 요구는 "대표만 **표출**"이지 "대표만 검색"이 아니다. 목록에서 왜 나왔는지는 상세에서 확인된다 |
| 목록의 "외 N명" | 넣었다 | 담당자를 3명 넣었는데 한 명만 보이면 나머지가 사라진 것처럼 읽힌다. 이름은 여전히 대표 하나뿐이다 |
| `Contact.orgId` | Organization FK 를 건다 | 계획서 초안에는 관계가 없었지만 다른 모든 모델과 같은 규칙이다. 값이 떠도는 문자열이 되면 조직 스코프 조회의 근거가 약해진다 |
| 거래처 `updatedAt` | 담당자 변경 시 **건드리지 않는다** | 그 값은 "회사 정보를 고친 시각"이다. 담당자를 한 명 넣을 때마다 목록(최근 수정일 내림차순) 순서가 뒤바뀌면 곤란하다 |

### 기회-6 예상 금액 — **확정 문서 기준** (결정됨)

합계나 "최신 견적서" 같은 암묵적 규칙 대신 **확정 문서 1건**을 두고 그 금액을 쓴다.
금액이 어느 문서에서 왔는지 화면에 드러나고, 견적서 1차·2차가 쌓여도 예측 가능하다.

**스키마**: `Opportunity.confirmedDocumentId` (nullable FK, named relation)
`Document.isConfirmed` 플래그보다 낫다 — 기회당 확정 문서가 **구조적으로 1건**으로 보장되고
"여러 문서가 동시에 확정" 상태가 만들어질 수 없다. `Opportunity` 에 자기참조 관계(다음 기회 체인)가
이미 있어 named relation 선례가 있다.

**① 자동 판정 (기본 동작)**

| 우선순위 | 문서 상태 |
|---|---|
| 1 | 계약완료 (COMPLETED) |
| 2 | 발송완료 (SENT) |
| 3 | 초안 (DRAFT) |
| — | **폐기(VOID)는 대상에서 제외** |

동순위는 최근 수정 순. 재판정 시점은 **문서 연결 · 상태 변경 · 금액 변경** 세 가지다.
판정은 순수 함수로 분리해 tsx 로 검증한다.

**② 변경 알림**

자동 판정으로 확정 문서가 바뀌면 금액이 소리 없이 달라진다. 반드시 알린다.

```
예상 금액이 ₩52,000,000 으로 바뀌었습니다 — 2차 견적서 기준   [되돌리기]
```

모달이 아니라 **toast** 로 한다. 작업 흐름을 막지 않으면서 되돌릴 길을 준다.

**③ 수동 고정**

사용자가 연관 문서 목록에서 다른 문서를 확정으로 지정하면 **그 기회는 자동 판정에서 제외(잠금)** 된다.
상세 화면에 "자동 판정으로 되돌리기" 를 둔다. 별도 설정 화면 없이 잠금 상태 자체가 자동/수동 스위치가 된다.

**④ 확정 문서가 없을 때 → ₩0**

수동 입력을 허용하지 않는다. 화면에는 `₩0 · 확정 문서 없음` 으로 표시하고 문서를 연결하도록 유도한다.

> ⚠️ **시드 재구성 필요**: 현재 시드는 기회 12건 중 문서가 연결된 것이 2건뿐이다.
> ₩0 규칙을 적용하면 파이프라인 합계가 **₩657,000,000 → 약 ₩96,000,000** 으로 급락한다.
> Phase 7 대시보드가 의미 있는 그림을 그리려면 **대부분의 기회에 문서를 연결하도록 시드를 다시 짠다.**
> 단계별 분포(초기·제안·검토/협상·수주·실주)와 문서 상태(초안·발송완료·계약완료)를 함께 배분한다.

> **재판정 시점**은 문서 연결(해제·삭제) · 상태 변경 · 금액 변경 세 가지이며, 각 라우트가 같은
> 트랜잭션에서 `syncOpportunityAmount()` 를 부른다. 자동 판정으로 확정 문서가 바뀌면 toast +
> [되돌리기](= 이전 문서로 수동 고정)로 알린다. 검증 **28건**(`pnpm test:confirmed-document`).
>
> **마이그레이션**: 테이블 재작성이지만 기존 컬럼을 전부 옮겨(`INSERT … SELECT`) **데이터 손실이 없다**.
> 다만 그대로 두면 "금액은 있는데 확정 문서는 없는" — 새 규칙으로는 만들어질 수 없는 — 상태가 남아
> 첫 문서 연결에서 손으로 넣은 금액이 조용히 덮인다. 그래서 **백필 SQL 을 덧붙여** 자동 판정을
> 1회 적용했다(순수 함수와 같은 순서). 덕분에 시드를 다시 돌리지 않아도 기존 DB 가 정합해진다.
>
> **시드 재구성 결과**: 기회 12건 중 **10건에 문서 연결**, 2건은 일부러 비워 `₩0 · 확정 문서 없음`
> 을 화면에서 확인할 수 있게 했다(`2027 연간 유지보수 갱신` · `네트워크 이중화 검토`).
> `인프라 증설 1차` 는 **수동 고정**(자동이면 2차 ₩88,000,000 → 고정한 1차 ₩92,000,000),
> `엔드포인트 보안 파일럿` 은 폐기 문서가 후보에서 빠지는 사례다.
> 파이프라인 합계는 우려했던 ₩96,000,000 이 아니라 **₩621,000,000**(진행 중 ₩381,000,000)이다.

## 진행 순서

```
A (결함 수정)  ─┐
B (목록 공통)  ─┼─▶ 서로 독립. 병렬 가능
D (담당자 다중) ┘      단 D 는 스키마 → 마이그레이션 충돌 주의

C (상세 재구성) ──▶ A 완료 후 (스테퍼를 함께 손대므로)

E (문서·금액)  ──▶ D 와 마이그레이션이 겹치므로 D 다음
```

**D · E 는 둘 다 스키마를 건드린다.** 마이그레이션 충돌을 피하려면 **D → E 순서로 직렬 진행**하고,
같은 시점에 두 워커를 띄우지 않는다.

**권장**: A+B 를 한 워커로 먼저 처리해 눈에 보이는 결함을 걷어낸 뒤,
C 를 단독 워커로(가장 큼), D 를 별도 워커로(스키마 격리), E 는 결정 후 마지막.
