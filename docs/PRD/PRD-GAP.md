이 문서는 **① 개발됐지만 PRD에 없는 것**, **② PRD에만 있고 개발되지 않은 것**, **③ 양쪽에 있지만 정의가 충돌하는 것** 세 축으로 갭을 정리한 트래킹 문서입니다.

## 0. 총평

현재 MVP는 **"문서(Document)를 중심축으로 한 문서 자동화 도구"** 이고, 새 PRD는 **"기회(Opportunity)를 중심축으로 한 CRM + 문서 자동화"** 입니다. 중심축이 다르기 때문에 갭이 단순 기능 누락이 아니라 **도메인 모델 재설계 수준**입니다.

| 구분 | 현재 구현 | PRD |
|---|---|---|
| 최상위 축 | `Document` (제목·금액·상태) | `Opportunity` (단계·예상금액·마감일) |
| 매출 집계 기준 | 문서 상태 `COMPLETED` 의 amount 합 | 기회 수주(`actual_close_date`) |
| 거래처 표현 | `Document.clientName` 문자열 | `Account` 엔티티 (1 : N 기회) |
| 문서 이력 | ✅ 버전 이력(rootId·version) + 확정본 다중 플래그 구현 | 버전 이력 + 확정본 플래그 |
| 없는 모듈 | — | CRM(거래처·기회), 기회 캘린더 |

## 4. 착수 전 결정이 필요한 3가지

1. **에디터 방식 (③-3)** — 블록 캔버스를 유지하고 PRD F-221을 수정할지, 리치 텍스트로 전환할지. **문서 관련 다른 모든 기능(PDF 출력·양식 변수 치환·AI 생성 출력 형식)이 여기에 종속**됩니다.
2. **문서 상태 vs 기회 단계 (③-1·2·5)** — `Opportunity` 도입 시 `COMPLETED(계약완료)` 를 제거해 문서 상태를 PRD의 3단계로 축소할지 결정해야, 대시보드 집계를 어느 기준으로 만들지가 정해집니다.
3. **Template 엔티티 도입 (③-4)** — F-201·F-202·F-204·F-522·F-523이 모두 여기에 묶여 있어, `Document.isCommon` 플래그 방식을 유지하면 조직 기능 전체가 막힙니다.

## 5. 권장 착수 순서 (참고)

PRD의 P0 의존 관계만 고려한 순서입니다.

1. **도메인 기반 마련** — `Account` · `Opportunity` 스키마 + 거래처/기회 CRUD (F-101·102·111)
2. **단계 관리** — 칸반 + 단계 전이 (F-112) → 발송 연동 자동 전이 (F-113·233·235) → 수주 처리 (F-115)
3. **문서 축 정합** — `Template` 엔티티 + 버전/확정본 (F-201·204·214) → 확정 견적서 기반 계약서 (F-213)
4. **출력 파이프라인** — PDF 생성·다운로드 (F-223) → 발송 시 자동 첨부 (F-232) → 실제 메일 전송
5. **캘린더** (F-301~306) — `Opportunity.expected_close_date` 확보 후 착수 가능
6. **대시보드 재작성** — 파이프라인·가중 예상 매출 (F-402·404)
7. **인증·권한** — 회원가입/로그인/워크스페이스 생성 → RBAC (F-501·511·512) → 7.1 테넌트 격리
