# PRD 구현 계획 (CRM · 캘린더 · 대시보드)

> 근거: `PRD_RainMaker.md` (v1.0 Draft, 2026-08-01)
> 작성일: 2026-08-06 · 상태: 착수 대기
> 관련: [SPEC.md](SPEC.md) · [ARCHITECTURE.md](ARCHITECTURE.md) · [BACKLOG.md](BACKLOG.md)

PRD 를 현 RAINMAKER 코드베이스에 얹기 위한 실행 계획이다. 기능마다 백엔드·프론트엔드를
모두 구현하며, **목업이 아닌 실제 동작**을 기준으로 완료를 판정한다.

## 1. 범위

### 포함

- 4.1 모듈 1 — 영업 기회 관리 (CRM)
- 4.2.3 문서 에디터

- 4.3 모듈 3 — 기회 캘린더

## 3. 착수 전 확인된 현 코드 상태

"실제 동작"으로 바꿔야 할 목업이 3개다.

| 항목 | 실제 | 근거 |
|---|---|---|
| PDF | `${doc.title}.pdf` 문자열만. 렌더링·다운로드 코드 없음 | `src/app/api/documents/[id]/send/route.ts:41` |
| 메일 발송 | `EmailLog` row 만 생성. 실제 전송 없음 | 같은 파일 `:33-50` |
| AI 생성 | 정규식으로 프롬프트 파싱. LLM 호출 없음 | `src/app/api/generate/route.ts:19-64` (범위 제외 — 유지) |

그 밖에 참고할 사실:

- `src/lib/session.ts` 는 데모 이메일 하드코딩으로 사용자/조직을 반환한다. 인증 도입 시 이 모듈만 교체하면 된다.
- `User` 모델에 비밀번호 필드가 없고, `/auth/login` 은 빈값 검사 후 `router.push` 만 하는 목업이다 (`login-form.tsx:26`). 회원가입 화면은 없다.
- `send/route.ts:27` 은 문서 조회 시 `orgId` 검사가 없다. **신규 라우트는 이 패턴을 따르지 말 것.**
- 칸반 드래그에 쓸 native HTML5 DnD 패턴이 `src/components/sidebar-folders.tsx:189-195` 에 이미 있다.
- 차트는 `recharts` 가 이미 설치돼 있다.

**추가 라이브러리는 PDF 렌더러와 메일 전송 모듈 2개뿐**이다.

## 4. 진행 원칙

### ① 마이그레이션은 1회로 묶는다

`Account` · `Opportunity` · `ActivityLog` · `Document.opportunityId` · `EmailLog` 트래킹 필드를
Phase 0 에서 한 번에 확정한다. 슬라이스마다 `db:migrate` 를 돌리면 SQLite 리셋 + Prisma
Client 재생성 + 타입 깨짐 왕복이 슬라이스 수만큼 곱해진다. 스키마는 PRD 6장에 이미 정의돼 있다.

### ② 상태 전이는 파일 하나에 모은다

F-113(발송→단계) · F-115(수주→매출·다음기회) · F-117(실주) · F-235(문서상태) · ActivityLog
기록이 전부 같은 트랜잭션 대상이다. `src/lib/opportunity-stage.ts` 에 도메인 함수로 두고
라우트는 호출만 한다. 라우트마다 흩뿌리면 PRD 9장이 경고한 "상태 정합성 엣지 케이스"가
그대로 버그가 된다.

### ③ 읽기 전용 집계는 마지막에

캘린더·대시보드는 모델이 흔들리면 전부 깨지고, 기회 데이터가 없으면 화면 검증도 불가하다.
집계는 `src/lib/pipeline.ts` 순수 함수로 빼서 캘린더 요약바(F-302)와 대시보드(F-402·F-404)가
같은 계산을 공유하게 한다.

### ④ 인증은 마지막 선택 단계

`getCurrentUser()` 추상화가 이미 있어 나중 도입 비용이 낮다. 재작업을 막으려면 **신규 라우트에
`orgId` 스코프 필터를 처음부터 넣는 규칙**만 지키면 된다.

## 5. Phase

### 슬라이스 내부 작업 순서 (고정)

```
API 라우트 + 검증(VAL_*)
  → 서버 컴포넌트 (목록/상세)
  → _components/ 클라이언트 폼
  → dev 서버로 실제 클릭 검증
  → pnpm typecheck · pnpm lint
  → 커밋
```

AGENTS.md 규칙대로 **서버 컴포넌트가 기본**이고 상호작용만 `_components/` 에 co-locate 한다.
UI 변경은 커밋 후 바로 PR 하지 말고 화면 확인 단계를 거친다.

### 8.1 상태 역전 규칙 — 현재 잠정 동작 (확정 전까지)

원칙은 "자동 전이는 앞으로만, 사람이 고른 전이는 그대로"다. 시스템이 임의로 단계를
내리면 담당자가 모르는 사이에 파이프라인 통계가 흔들린다.

| 상황 | 현재 동작 | 결과 |
|---|---|---|
| 견적서 재발송 (이미 검토/협상) | 단계 유지, 발송 이력만 기록 | `skipped` / `no-downgrade` |
| 수주·실주된 기회에 문서 발송 | 단계 유지, 발송 이력만 기록 | `skipped` / `already-closed` |
| NDA·제안서 발송 | 전이 규칙 없음, 이력만 기록 | `skipped` / `not-applicable` |
| 담당자가 칸반에서 직접 되돌림 | 그대로 전이. 마감 → 진행 단계로 되돌리면 확정일·실주 사유를 비운다 | `changed` |

Phase 3 착수 전 확정할 질문:

1. 재발송이 단계를 되돌려야 하는가? (현재: 되돌리지 않음)
2. 발송 취소·문서 폐기(VOID) 시 자동 전이를 취소해야 하는가? (현재: 미처리 — 문서 상태만 바뀌고 단계는 그대로 둔다)
3. 되돌린 이력을 타임라인에 어떻게 보이는가? (현재: `STAGE_CHANGED` 1건이 앞뒤 단계와 함께 추가로 쌓인다)
4. 수주(WON)를 되돌리면 F-115 로 생성된 다음 기회는 어떻게 되는가? (현재: 미처리)

### 8.2 F-404 단계별 확률 — 결정 대기

`weightedForecast(opportunities, probabilities)` 는 확률 테이블을 **필수 인자**로 받는다.
코드에 기본 수치를 넣지 않은 이유는, 근거 없는 숫자라도 화면에 뜨는 순간 담당자가 그 값을
믿고 판단하기 때문이다. 나중에 수치를 바꾸면 과거 대시보드와 비교도 불가능해진다.

Phase 7 착수 전 확정할 항목:

| 결정 | 선택지 | 메모 |
|---|---|---|
| 확률 출처 | 코드 상수 · 조직별 설정(관리자 콘솔) · 과거 수주 데이터 기반 산출 | MVP 는 상수가 현실적. 데이터 기반은 표본이 쌓인 뒤 |
| 수치 | 초기 · 제안 · 검토/협상 3개 값 | 팀 합의 필요. 실적 데이터가 있으면 그 승률을 쓴다 |
| 마감 단계 취급 | 확률표에 수주=1 · 실주=0 을 넣어 전체 집계 vs 진행 중 기회만 집계 | 함수가 `openOnly` 옵션으로 둘 다 지원한다 |
